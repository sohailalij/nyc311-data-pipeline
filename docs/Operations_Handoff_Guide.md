# Operations Handoff Guide

## Purpose

This document is for someone who did not build this pipeline but needs to
run it, refresh it, or fix it when something breaks. It assumes no prior
context beyond basic comfort with a terminal, Python, SQL, and Git.

The pipeline itself is a set of independent Python scripts run in
sequence, not a long-running service. There is no server process to keep
alive day to day. "Operating" this system means running the right script
in the right order and knowing what to check when one of them fails.

---

## 1. System Prerequisites

- **Java 17** (Eclipse Temurin build). PySpark 3.5 needs Java 8, 11, or
  17, this project standardizes on 17.
- **Python 3.9 to 3.11**. PySpark 3.5 does not support 3.12 or 3.13.
  This project was built and tested on 3.11.9.
- **PySpark, installed via pip only.** Do not install a separate
  standalone Spark distribution or set a `SPARK_HOME` environment
  variable. `pip install -r requirements.txt` provides everything Spark
  needs to run locally. A standalone Spark install on the same machine
  will silently override the pip-installed version and cause a version
  mismatch between the Python and JVM sides (see section 12).
- **winutils.exe and hadoop.dll**, matching Hadoop 3.3.5 (the version
  bundled inside PySpark 3.5.x). Required on Windows even for purely
  local file operations, Spark's file commit step will fail without it.
- **PostgreSQL**, running locally, with a database created for this
  project (`nyc311_analytics` by default, configurable).
- **An AWS account with an IAM user scoped to a single S3 bucket only**
  (`nyc311-pipeline-sohail-2026`). No other AWS service is required.
- **Git**, for cloning the repository and, eventually, for Jenkins to
  pull from.

## 2. Environment Configuration

Environment variables needed, all at the Machine (System) level unless
noted:

| Variable | Value | Notes |
|---|---|---|
| `JAVA_HOME` | Path to the JDK 17 install | Must not contain spaces |
| `HADOOP_HOME` | Folder containing `bin\winutils.exe` and `bin\hadoop.dll` | Also copy `hadoop.dll` into `C:\Windows\System32` |
| `SPARK_HOME` | Must not be set | Delete it if present |
| `PATH` | Must include `%JAVA_HOME%\bin`, `%HADOOP_HOME%\bin`, and the standard Windows system paths (`C:\Windows\system32`, `C:\Windows`) | See section 12 if PATH appears to be missing standard entries |
| `PG_HOST` | e.g. `localhost` | Defaults to `localhost` if unset |
| `PG_PORT` | e.g. `5432` | Defaults to `5432` if unset |
| `PG_DB` | e.g. `nyc311_analytics` | Defaults to `nyc311_analytics` if unset |
| `PG_USER` | e.g. `postgres` | Defaults to `postgres` if unset |
| `PG_PASSWORD` | your Postgres password | Required, no default, the load script raises an error and stops if this isn't set |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | IAM credentials for the S3 bucket | Never store these in a file |

`config/config.yaml` (copied from `config/config.example.yaml`) holds
non-secret settings, paths, Spark tuning, the acquisition date range.
Credentials never go in this file, only environment variables.

**Important:** any environment variable change requires closing every
open terminal completely (and restarting VS Code entirely, if that's
where you're working) before it takes effect. A terminal keeps the
environment it had when it was opened.

## 4. Database Configuration

PostgreSQL holds two summary tables and one reporting view, defined in
`sql/postgres/create_schema.sql`:

- **`borough_category_monthly_summary`** — `created_year`, `created_month`
  (checked between 1 and 12), `borough`, `complaint_category`,
  `total_requests`, `avg_resolution_hours`, `closed_requests`,
  `unresolved_requests`. A `UNIQUE` constraint on
  `(created_year, created_month, borough, complaint_category)` prevents
  duplicate summary rows for the same combination. Indexed on
  `(created_year, created_month)` and on `borough`.
- **`borough_category_daily_summary`** — same shape, keyed by
  `request_date` instead of year/month, with the equivalent `UNIQUE`
  constraint and indexes on `request_date` and `borough`.
- **`category_totals_ytd`** (view) — sums `total_requests` and averages
  `avg_resolution_hours` per `complaint_category` across the whole
  monthly table, ordered highest volume first. This is the one object
  meant for a business user to query directly rather than a
  transformation intermediate.

Run `create_schema.sql` against a fresh database before the first load.
All three `CREATE` statements use `IF NOT EXISTS` / `OR REPLACE`, so
re-running the script against an existing database is safe and won't
error out.

`load_to_postgres.py` truncates each target table and reinserts
everything on every run via a plain `INSERT` (`psycopg2.extras.execute_values`,
batches of 5,000 rows), not an upsert. The `UNIQUE` constraints exist to
catch a genuine bug (duplicate summary rows coming out of Hive) rather
than to support conflict resolution, if the `TRUNCATE` step is ever
skipped or fails silently, a rerun will hit a constraint violation
instead of quietly overwriting old rows. That's a feature here, not an
oversight, a silent duplicate would be worse than a loud failure.

Before inserting, every row passes through `clean_row()` in
`postgres_helpers.py`. This exists specifically because a Spark `NULL`
average (from boroughs with zero closed requests) turns into a Pandas
`NaN` once converted to a DataFrame, and `psycopg2` will happily insert
the literal string `"NaN"` instead of SQL `NULL` if nothing catches it
first. That silently broke `AVG()` in `category_totals_ytd` during
development. `clean_row()` is the fix, and it's covered by
`tests/test_postgres_helpers.py`, don't remove it without understanding
why it's there.

## 5. Hive Configuration

There is no standalone Hive server here. Hive support comes from
Spark's own embedded metastore (`enableHiveSupport()`), backed by a
local Derby database. Running any Hive-enabled script creates
`metastore_db/` and `spark-warehouse/` folders in the project root the
first time it runs, both are git-ignored.

Database: `nyc311_analytics_db`. Three tables live in it:

- **`service_requests`** — external, partitioned by `created_year` and
  `created_month`, pointing at `data/processed/cleaned_311_requests`
  via an absolute `file:///` URI, not a relative path. Built by
  `create_hive.py`, which drops and recreates it on every run, so
  rerunning it is always safe and is the correct fix if the table ever
  gets into a bad state.
- **`borough_category_monthly_summary`** and
  **`borough_category_daily_summary`** — managed tables built by
  `build_summary_tables.py` via `CREATE TABLE AS SELECT`, grouping
  `service_requests` by year/month or by day, borough, and complaint
  category. Both are dropped and rebuilt on every run for the same
  idempotency reason.

`build_summary_tables.py` also runs the project's window function
query directly against Hive, ranking each borough's top complaint
category per month with
`RANK() OVER (PARTITION BY borough, created_month ORDER BY total_requests DESC)`,
filtered to rank 1. This satisfies the window-function requirement from
the project plan and is worth knowing about if a reviewer asks where
that shows up.

Both summary builds include a built-in reconciliation check,
comparing `SUM(total_requests)` from the summary table against
`COUNT(*)` from the raw `service_requests` table. If those two numbers
ever diverge, something is wrong with the `GROUP BY` logic, not a
minor discrepancy to shrug off.

One thing worth knowing explicitly: `MSCK REPAIR TABLE`, the usual way
to register partitions for an external table, silently found zero
partitions when tried on this Windows setup. `ALTER TABLE
service_requests RECOVER PARTITIONS` is what actually works here, and
that's what `create_hive.py` uses. If you're extending this script and
reach for `MSCK REPAIR TABLE` out of habit, it will look like it
succeeded and then queries will return nothing.

## 6. Spark Job Execution

Run stages from the project root, in this exact order:

```
python src/acquisition/download_311_data.py
python src/reference/build_reference_tables.py
python src/ingestion/validate_and_ingest.py
python src/transformation/clean_311_data.py
python src/hive/create_hive.py
python src/hive/build_summary_tables.py
$env:PG_PASSWORD = "..."; python src/postgres/load_to_postgres.py
```

`clean_311_data.py` runs Spark with `local[4]`, 4 GB driver memory, and
16 shuffle partitions. These aren't arbitrary, a default configuration
ran out of heap memory on the full 3.2 million row dataset during a
wide shuffle. If you see an OutOfMemoryError on a machine with less
RAM, lower `local[4]` to `local[2]` and reduce shuffle partitions
before increasing driver memory, since driver memory is capped by
whatever's actually available on the machine.

Every stage prints its own row count and, where relevant, checks that
count against the previous stage's output. That's the main built-in
correctness check, not a separate monitoring tool.

## 7. Jenkins Pipeline

The `Jenkinsfile` at the repo root defines three stages: Environment
Check (confirms Python, pytest, and Java are reachable), Unit Tests
(`test_transform_functions.py` and `test_postgres_helpers.py`), and
Data Quality Tests (`test_data_quality.py` against the real 3.2 million
row output). Results publish as JUnit XML from `reports/`, and the
build fails if any test fails.

Important scope note: this pipeline validates the code and the already-
produced data, it does not run the acquisition-through-load pipeline
itself. Someone expecting Jenkins to regenerate the data end to end on
every commit will be surprised, that's a manual, scripted process
(section 9), not something CI currently automates.

The `PROJECT_DIR` and `PYTHON` environment values in the Jenkinsfile
are hardcoded to this specific machine's path
(`D:\nyc311-data-pipeline`). Moving Jenkins to a different machine or
agent requires updating both of those first.

## 8. Deployment Procedure

There's no server to deploy to. "Deployment" here means:

1. Clone the repository onto a machine meeting section 1's
   prerequisites.
2. Set up the environment per section 2.
3. Copy `config/config.example.yaml` to `config/config.yaml`.
4. Run the stages in section 6's order.

For the cloud portion: run `src/aws/s3_test.py` first to confirm the
IAM credentials and bucket access actually work before running
`src/aws/upload_to_s3.py`, which mirrors the curated Parquet output to
the `nyc311-pipeline-sohail-2026` bucket. There's no compute running in
AWS, only storage, so there's nothing further to deploy on the cloud
side.

## 9. Data Refresh Procedure

To pull a new period of NYC 311 data:

1. Rerun `download_311_data.py` with new `--start`/`--end` values. It
   resumes automatically from wherever a prior run left off, based on
   the last `(created_date, unique_key)` pair written, so it's safe to
   interrupt and rerun.
2. Rerun `build_reference_tables.py` against the new raw file. Do this
   before ingestion, or ingestion will flag anything genuinely new
   (an agency code or complaint type that didn't exist in the old
   window) as unknown.
3. Rerun `validate_and_ingest.py`, `clean_311_data.py`,
   `create_hive.py`, `build_summary_tables.py`, and
   `load_to_postgres.py`, in that order.
4. Re-run `upload_to_s3.py` if the S3 copy needs to reflect the new
   data too.
5. Refresh the Tableau workbook. Tableau Public cannot hold a live
   connection to a local Postgres database, since it isn't reachable
   from the internet, so the workbook's extract has to be refreshed
   locally and republished manually each time the underlying data
   changes.

Nothing in this pipeline is incremental. Every stage from ingestion
onward processes the entire dataset again, there's no append-only or
delta mode currently built in.

## 10. Logs and Log Locations

Being direct about this: right now, logging is console output only.
The acquisition, reference, and ingestion scripts use Python's
`logging` module writing to stdout, nothing is persisted to a file on
disk. If you need to see what happened during a run after the fact and
you didn't capture the terminal output yourself, that information is
gone, with one exception: Jenkins keeps the full console output of
every build in its own build history, plus the JUnit XML files under
`reports/`.

## 11. Monitoring

There's no dashboard or alerting layer watching this pipeline. What
exists instead:

- Jenkins build status (pass or fail) after each run of the test
  suite.
- Each script's own printed output: acquisition's manifest JSON,
  ingestion's `ingestion_report.json` with pass rate and threshold
  checks, the reference builder's conflict and category-coverage
  report, Hive's partition and row count queries, and the load
  script's Hive-versus-Postgres row count comparison.
- The Tableau dashboard itself, as a final eyeball check that the
  numbers on screen look reasonable after a refresh.

If something needs continuous monitoring beyond "did the last manual
run succeed," that's not built yet.

## 12. Common Failures

These are real failures hit during development, not hypothetical ones:

- **`Py4JError: Constructor ... does not exist`** — caused by a
  standalone Spark distribution on the machine with `SPARK_HOME` set,
  conflicting with the pip-installed PySpark version. Fix: delete
  `SPARK_HOME`, reinstall the pip-pinned PySpark version.
- **`UnsatisfiedLinkError` during a Parquet write** — `winutils.exe` is
  present but its matching `hadoop.dll` isn't, or the versions don't
  match the installed PySpark's bundled Hadoop client. Fix: use the
  Hadoop 3.3.5 pair for PySpark 3.5.x, and make sure `hadoop.dll` is in
  both `HADOOP_HOME\bin` and `C:\Windows\System32`.
- **OutOfMemoryError during transformation** — a full shuffle across
  3.2 million rows without enough driver memory. Fixed with
  `local[4]`, 4 GB driver memory, 16 shuffle partitions, and avoiding
  an unnecessary explicit `.repartition()` call before the write.
- **`MSCK REPAIR TABLE` finds zero partitions** — known not to work
  reliably in this setup on Windows. Use
  `ALTER TABLE ... RECOVER PARTITIONS` with an absolute `file:///`
  location instead.
- **A Postgres `AVG()` returns garbage or the column looks like text**
  — a Spark `NULL` became a Pandas `NaN` became the literal string
  `"NaN"` in Postgres. `postgres_helpers.clean_row()` exists to prevent
  this, confirm it's actually being called if this resurfaces.
- **Spark looks for a `python3` executable that doesn't exist** — a
  Windows-only issue, since there's no `python3` alias by default.
  Point `PYSPARK_PYTHON` at the venv's actual `python.exe`.
- **A command works in one terminal but not another** — almost always
  a stale environment. Close every terminal (and VS Code, if that's
  where it's running) completely and reopen before concluding a fix
  didn't work.
- **`where.exe`, `taskkill`, or similar system commands stop being
  recognized** — the Machine-level PATH is missing standard Windows
  entries. Check with
  `[Environment]::GetEnvironmentVariable("Path", "Machine")` in an
  elevated PowerShell, rebuild it if it's empty or missing
  `C:\Windows\system32` and `C:\Windows`.

## 13. Troubleshooting

Quick diagnostic commands for the failures above:

```powershell
# Confirm which PySpark version is actually installed
python -c "import pyspark; print(pyspark.__version__)"

# Confirm SPARK_HOME is not set
echo $env:SPARK_HOME

# Confirm Java version and location
java -version
echo $env:JAVA_HOME

# Check a Machine-level variable directly (bypasses stale terminal state)
[Environment]::GetEnvironmentVariable("SPARK_HOME", "Machine")
[Environment]::GetEnvironmentVariable("JAVA_HOME", "Machine")
[Environment]::GetEnvironmentVariable("Path", "Machine")

# Confirm a system command resolves and from where
where.exe java
```

Changing any Machine-level environment variable requires an elevated
(Run as administrator) PowerShell. A non-elevated attempt fails with a
`SecurityException`, sometimes without obviously saying why.

## 14. Recovery Procedures

- **Acquisition interrupted partway through** — just rerun the exact
  same command. It reads the last row already written and resumes from
  there, it does not start over.
- **Ingestion, reference build, or transformation fails midway** —
  these scripts overwrite their own output files on each run, so
  simply rerun them. There's no partial-state cleanup needed.
- **Hive table in a bad state** — rerun `create_hive.py`, it drops the
  table first regardless of its current state.
- **Postgres load fails partway through** — the target table was
  already truncated before the insert began, so it may currently be
  empty. Rerun `load_to_postgres.py` fully, there's no safe way to
  resume a partial load, only to redo it.

## 15. Restart/Shutdown Procedures

Nothing in this pipeline runs as a persistent service, every script
starts, does its work, and exits. There's no daemon to restart.

If a Spark script is force-killed (Ctrl+C or closing the terminal
mid-run) rather than allowed to finish, check Task Manager for orphaned
`java.exe` processes and end them manually. Spark's own shutdown hook
normally cleans these up via `taskkill`, but that fails silently if
PATH is broken (section 12).

PostgreSQL runs as a Windows service outside this project. If the load
script can't connect, check that service's status and restart it
through Windows Services if needed.

## 16. Backup Considerations

Raw data, reference tables, and cleaned Parquet output are all
regenerable from NYC Open Data and the pipeline scripts, they are
intentionally git-ignored and not backed up as files. The actual
sources of truth worth protecting are:

- The code and configuration in Git, already backed up via GitHub.
- The PostgreSQL database, if you've made any manual changes to it
  beyond what the load script produces, take a `pg_dump` before
  anything risky like a schema change.

The S3 copy of the curated Parquet output is a secondary location for
that data, not a substitute for an actual backup strategy.

## 17. Known Limitations

- The Jenkinsfile hardcodes an absolute Windows path
  (`D:\nyc311-data-pipeline`) and a specific venv Python path. It will
  not run on a different machine or a non-Windows agent without
  editing those two values first.
- No log files are written to disk, only console output. Historical
  debugging outside of a captured terminal session or a Jenkins build
  log isn't possible right now.
- The Postgres load uses a plain `INSERT`, not an upsert. It relies on
  the `TRUNCATE` step running successfully first. If that step is ever
  skipped, a rerun will fail on the `UNIQUE` constraint rather than
  silently duplicating or overwriting rows, by design, but worth
  knowing before assuming a failed load can just be re-run blindly.
- There's no scheduler. Every stage is triggered manually.
- No license file exists yet in the repository.
- This is a single-user, local setup. Two people running the pipeline
  against the same Postgres database at the same time would conflict
  during the truncate step.
- The Tableau Public dashboard requires a manual extract refresh and
  republish, it has no live connection back to this pipeline's data.

## 18. Escalation Information

This is a personal project without a formal support team, so there's
no on-call rotation or ticketing system to escalate to. In practice:

- Open an issue on the GitHub repository
  (https://github.com/sohailalij/nyc311-data-pipeline/issues) to keep
  a record of any problem found.
- The project's sole maintainer is the repository owner. Anyone else
  operating this pipeline should treat this document, plus the other
  files in `docs/`, as the first and only line of support before
  reaching out directly.
